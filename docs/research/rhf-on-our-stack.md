# react-hook-form on our stack: version, React Compiler, RN integration

Research for [#99](https://github.com/Wojtas399/bh-cycling-app/issues/99) (map: [#98](https://github.com/Wojtas399/bh-cycling-app/issues/98)). Researched 2026-10-14.

Our stack: Expo SDK 57, React 19.2.3, React Native 0.86.3, React Compiler on (`app.config.ts` → `experiments.reactCompiler: true`, `babel-plugin-react-compiler@1.0.0` from `package-lock.json`), `eslint-plugin-react-hooks@7.1.1`, TanStack Query v5, jest-expo 57 + `@testing-library/react-native@14`.

Sources: RHF GitHub releases and issues, RHF source on `master`, the RHF docs **source** repo (`react-hook-form/documentation`; react-hook-form.com returns HTTP 403 to fetchers, so I read the `.mdx` files the site is built from), React Compiler source, and react.dev.

---

## TL;DR

1. **Use `react-hook-form@^7.90.0`, not v8.** v8 is still a beta (`8.0.0-beta.4`, 2026-09-26). The v8 PR is still open. `@hookform/resolvers@5.9.1` declares a peer of `react-hook-form: ^7.55.0`. And beta.4 was cut _before_ the latest Compiler-related `errors` fix (#13791), which shipped in 7.90.0.
2. **React Compiler:** the remaining v7 hazards are `watch()`, which the compiler skips on purpose, and mutated or stable references. Recent v7 releases fixed the `errors`-reference bugs that matter to us (7.79.0, 7.90.0). Rules: never call `watch()`, use `useWatch`/`useFormState`, destructure `formState` fields at the top of the hook, and prefer `useController` over `<Controller render>`. Keep `'use no memo'` as a per-function escape hatch, not the default.
3. **RN integration:** the official docs use `Controller` with `onChangeText={field.onChange}`, `onBlur`, `value`. For a reusable `FormField`, use `useController`. Pass `field.ref` into our `forwardRef` `Input`. `setFocus`, `shouldFocusError` and `setError(..., { shouldFocus })` then work, because RHF only calls `.focus()` on the ref.
4. **Keeping today's UX** ("validate on submit, clear on change") needs `mode: 'onSubmit'` (the default). It also needs either `reValidateMode: 'onSubmit'` plus `clearErrors(name)` in the change handler, or the RHF default `reValidateMode: 'onChange'`. The default re-validates on each change rather than just clearing, which is a small UX change.
5. **Async submit:** `handleSubmit` re-throws errors from `onValid`. `isSubmitting` covers the awaited `onValid`. So call `mutateAsync` inside try/catch and map server errors with `setError(field | 'root.x')`, or call `mutate` and keep using `mutation.isPending`.
6. **Testing with `renderHook`:** this works, and RHF's own tests do it. But with no component rendered, no field is _registered_. `Controller`/`useController` `rules` therefore never run in a hook test. Validation must live where `handleSubmit` can see it without the UI: a `resolver` (schema, testable in `lib/`) or `register(name, rules)` called inside the hook.

## 2. React Compiler compatibility

### What the compiler itself does

- `babel-plugin-react-compiler@1.0.0` (our version) hard-codes RHF in its module type provider. Only `useForm().watch` is marked `knownIncompatible`, with the message: "React Hook Form's `useForm()` API returns a `watch()` function which cannot be memoized safely." Comment in the source: "Only the `watch()` function returned by react-hook-form's `useForm()` API is incompatible". ([DefaultModuleTypeProvider.ts](https://github.com/facebook/react/blob/main/compiler/packages/babel-plugin-react-compiler/src/HIR/DefaultModuleTypeProvider.ts); I confirmed the string is in the published 1.0.0 `dist/index.js`.)
- react.dev, `incompatible-library` lint (part of `eslint-plugin-react-hooks` v7, which we use): "React Compiler can automatically skip over components that use these incompatible APIs". For RHF it recommends `useWatch({ control, name })` instead of `watch('field')`. ([react.dev: incompatible-library](https://react.dev/reference/eslint-plugin-react-hooks/lints/incompatible-library))
- `'use no memo'` "should be used sparingly and temporarily … a temporary escape hatch". It works at function or module level and must be the first statement. ([react.dev: "use no memo"](https://react.dev/reference/react-compiler/directives/use-no-memo))

### Why the hazards exist (from the RHF source and docs)

- `useForm` returns the **same object** every render (`return _formControl.current`). Only `formState` is replaced, via `useMemo(() => getProxyFormState(formState, control), [control, formState])`. ([useForm.ts](https://github.com/react-hook-form/react-hook-form/blob/master/src/useForm.ts)) A compiled hook that memoizes on `form` alone (for example `return { form, error: form.formState.errors.x }`) can therefore go stale.
- `formState` is a Proxy that subscribes only to the keys you read during render. The docs say to "read all formState values to subscribe", not conditionally (`!isDirty || !isValid` short-circuits). ([formstate.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/formstate.mdx))

### Rules for our codebase (derived from the above)

1. Require **≥ 7.90.0**.
2. Never call `useForm().watch()`. Use `useWatch({ control, name })` or `useFormState({ control, name })`. The compiler bails out on `watch`, and `react-hooks/incompatible-library` flags it.
3. In the form hook, destructure the `formState` fields you need unconditionally, at the top (`const { errors, isSubmitting } = formState`), and derive return values from those values, not from the `form` object.
4. Read errors as `errors.fieldName?.message`, not via RHF internals.
5. Build field components on `useController`, not `<Controller render>`, following the community finding in #12298. The official docs show both.
6. Treat `'use no memo'` as a debugging escape hatch for a specific function, not a blanket rule. This matches react.dev guidance. The prototype ticket should confirm on device.

## 3. React Native integration

- **Official RN pattern** (Get Started → React Native; Controller docs): wrap inputs with `Controller`, and wire `onBlur={onBlur}`, `onChangeText={onChange}`, `value={value}`. "To integrate with input component, you can wrap it with `Controller`." ([get-started.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/get-started.mdx), [controller.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/usecontroller/controller.mdx)). `register` spreading does not apply to RN `TextInput` (no DOM `onChange` event or `name`). `useForm` option popups say "React Native: compatible with Controller" ([useform.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform.mdx)).
- **`useController` vs `Controller`:** "`useController` … powers `Controller` … shares the same props and methods … useful for creating reusable Controlled input." ([usecontroller.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/usecontroller.mdx)) This fits a reusable `FormField`, and given §2 it is also the safer choice under the compiler.
- `field.onChange` takes a value ("value should **not be `undefined`**"), so `onChangeText={field.onChange}` works directly. Always provide `defaultValues` (e.g. `''`), or the input starts uncontrolled. (usecontroller.mdx `defaultValue` row)
- **Ref forwarding and focus:** `field.ref` docs: "Assign `ref` to component's input ref to allow hook form to focus the error input." In v7 the callback ref wraps the element as `{ focus: () => elm.focus(), select, setCustomValidity, reportValidity }`, with each call guarded by `isFunction`. ([useController.ts](https://github.com/react-hook-form/react-hook-form/blob/master/src/useController.ts)) RN `TextInput` has `.focus()`, so `<Input ref={field.ref} />` (our `forwardRef<TextInput>`) is enough for:
  - `shouldFocusError` (default `true`): "focus is set on the first field with an error"; "focus order is based on the `register` order". It only works when a ref is attached. ([useform.mdx#shouldFocusError](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform.mdx))
  - `setFocus(name)`: calls `ref.focus()` inside a `setTimeout`. Docs: "Avoid calling `setFocus` right after `reset`". ([setfocus.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/setfocus.mdx), `createFormControl.ts`)
  - `setError(name, err, { shouldFocus: true })`: "only works when the input's reference is registered". ([seterror.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/seterror.mdx))
- Our current `Input` forwards `ref` to the inner `TextInput` (`components/Input.tsx`), so no component change is needed for focus. One note for later: React 19 allows `ref` as a plain prop, so `forwardRef` is optional, but nothing forces a change.

## 4. APIs relevant to our forms

### `mode` / `reValidateMode`

- `mode` default `'onSubmit'`: "Validation is triggered on the `submit` event, and inputs attach `onChange` event listeners to re-validate themselves." `reValidateMode` default `'onChange'`: re-validation after submit "occurs during the input change event". Both are reactive since 7.56.0. ([useform.mdx#mode](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform.mdx))
- **Today's UX is "validate on submit, clear on change".** RHF's default re-validates on change. A required-field error disappears once the user types, but a "too short" error stays until the value is valid. That differs from clear-on-change. To keep the exact current UX, use `reValidateMode: 'onSubmit'` and call `clearErrors(name)` in the field change handler (and reset the mutation, as today). This is a design decision for the grilling ticket.

### `setError` / `clearErrors`

- `setError(name, { type, message }, { shouldFocus })`. `root.*` keys hold form-level/server errors and "will not persist with each submission". An error on a registered field "will not persist … if the input passes `register`'s associated rules" (it is overwritten by the next validation). It forces `isValid` to false. Avoid field names `type`, `root`, `ref`, `types`, `message`, `form`. ([seterror.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/seterror.mdx))
- `clearErrors(name?)` "does not affect the validation rules attached to inputs and does not impact `formState.isValid`". ([clearerrors.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/clearerrors.mdx))
- Our `*Errors.ts` mappers (server code → field or form error) map directly onto `setError(field)` / `setError('root.server')`. This needs ≥ 7.90.0 under the compiler (#13790).

### `handleSubmit` with TanStack mutations; `isSubmitting`

- Signature: `handleSubmit(onValid, onInvalid?)` returns `(e?) => Promise`. Since 7.84.0 it resolves with `onValid`'s return value. "`handleSubmit` function will not swallow errors that occurred inside your onSubmit callback … use try/catch … Use `setError` inside the catch block … this also ensures `formState.isSubmitSuccessful` is set to `false`." ([handlesubmit.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/handlesubmit.mdx))
- Source: `isSubmitting: true` is emitted before validation, then `await onValid(...)` runs, then `isSubmitting: false`, then any `onValid` error is re-thrown. Invalid forms run `onInvalid` and then `_focusError()`. ([createFormControl.ts `handleSubmit`](https://github.com/react-hook-form/react-hook-form/blob/master/src/logic/createFormControl.ts))
- `isSubmitting`: "`true` if the form is currently being submitted". ([formstate.mdx](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform/formstate.mdx))
- Two consistent patterns:
  - **A.** `onValid = async (v) => { try { await mutation.mutateAsync(v) } catch (e) { mapError(e) → setError(...) } }`. `isSubmitting` then tracks the whole request, and no rejection escapes to `onPress`.
  - **B.** `onValid = (v) => mutation.mutate(v, { onError: e => setError(...) })` and keep using `mutation.isPending` as `loading`. `isSubmitting` is then only true during validation.
  - Avoid `mutateAsync` without try/catch: the re-thrown rejection becomes an unhandled promise rejection from `onPress={handleSubmit(...)}`.

### Form-level `validate` (FYI)

- Since 7.72.0, `useForm({ validate })` gives form-level validation without a schema library. Field errors from it surface at `errors.form.<field>`, not `errors.<field>`, and it is ignored when a `resolver` is set. ([useform.mdx#validate](https://github.com/react-hook-form/documentation/blob/master/src/content/docs/useform.mdx)) This shape doesn't fit our per-field error display, so a `resolver` is likely the better fit.

## 5. Testing `useForm`-based hooks with `renderHook` (jest-expo + RNTL 14)

- RHF's own test suite drives `useForm` through `renderHook` + `act`, for example `const { result } = renderHook(() => useForm()); await act(async () => { await result.current.handleSubmit(cb)(...) })`. ([handleSubmit.test.tsx](https://github.com/react-hook-form/react-hook-form/blob/master/src/__tests__/useForm/handleSubmit.test.tsx); same pattern in `setError.test.tsx` and `useForm.test.tsx`.) The pattern is supported.
- RNTL 14: `renderHook` is **async** and must be awaited; `rerender`/`unmount` are async too. Wrap state-changing calls in `await act(...)`. ([RNTL renderHook docs](https://oss.callstack.com/react-native-testing-library/docs/api/misc/render-hook)) Our existing suites already do this (`app/(app)/change-password/__tests__/useChangePassword.test.ts`).
- RHF docs (Advanced → Testing Form): with React Native you don't need `@testing-library/jest-dom`. They suggest a setup file with `global.window = {}; global.window = global`. ([advanced-usage.mdx#TestingForm](https://github.com/react-hook-form/documentation/blob/master/src/content/advanced-usage.mdx)) jest-expo already provides a `window` global, so verify this in the prototype before adding it.
- **Key constraint (from the source):** without a resolver, `handleSubmit` runs `executeBuiltInValidation({ fields: _fields })`, which covers _registered_ fields only. `Controller`/`useController` register a field only when their component renders. In a `renderHook` test no field component renders, so `rules` on `useController` never run and submit always looks valid. With a `resolver`, `handleSubmit` runs `_runSchema()` over all form values, so validation works headlessly. ([createFormControl.ts](https://github.com/react-hook-form/react-hook-form/blob/master/src/logic/createFormControl.ts)) Options:
  1. Use a **resolver/schema** (e.g. zod via `@hookform/resolvers`, peer `^7.55.0`). The schema can be unit-tested in `lib/`, and hook tests via `renderHook` + `setValue`/exposed change handlers + `handleSubmit` stay meaningful. This best fits CODING_STANDARDS ("business logic in hooks/`lib/`, no UI tests").
  2. Call `register(name, rules)` inside the hook (custom register, no element). This keeps rules headless, but `shouldFocusError` then needs the `useController` ref to be attached as well.
- Driving values in hook tests: call `result.current.setValue(name, v)` (pass `{ shouldValidate: true }` to mimic re-validation), or expose `onChange` handlers from the hook as today. Remember the mutation-settle tick our suites already use (`await act(() => new Promise(r => setTimeout(r, 0)))`).
