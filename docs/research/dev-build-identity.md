# Research: what a third app identity needs for the Dev build

Ticket: #314 (map #313). Date: 2026-11-09.

Question: a third app, bundle ID / package `com.wojtas.blackhorsecyclingapp.dev`, EAS profile, channel and `APP_ENV` all `dev`, EAS internal distribution (iOS ad hoc, Android APK), reusing the staging backend. What does every bundle-ID- or `APP_ENV`-keyed thing need?

## Gist

Most of it can be shared with staging. The Dev build needs **its own Firebase iOS app and Android app inside the staging project** (free), **its own iOS plist** as a new EAS file variable, **the Dev keystore's SHA-1 on the new Firebase Android app** so Google Sign-In works, and **a first interactive `eas build` per platform** so EAS creates the new credentials (ad hoc profile and keystore). The Intervals.icu client, the Cloud Functions, Firestore, the Google web client ID and the EAS `development` environment are all shared. Two things can't simply be shared: the **iOS plist** (one per bundle ID) and the **Android OAuth client** (one per package + SHA-1). One risk is worth a decision: the **shared `blackhorsecyclingapp` URL scheme** on Android when staging and Dev are both installed.

## Risk: the shared URL scheme on Android

Staging, Dev and production all register `blackhorsecyclingapp://`. On **iOS**, `expo-web-browser`'s auth session (`ASWebAuthenticationSession`) hands the callback to the app that started the session, so a shared scheme is fine. On **Android**, the flow uses Custom Tabs plus `Linking`, and the redirect is an ordinary `VIEW` intent. With two installed apps claiming the scheme, Android may show a chooser or send the code to the wrong app (staging instead of Dev). I found no primary source that confirms what Custom Tabs does here, so this is **inferred** from how Android resolves intents. Expo's own guidance for app variants is to make identifiers unique per variant.

Options:

- **A. Keep the shared scheme.** No Intervals.icu change. Accept a possible chooser on Android when you connect Intervals.icu (once per account; the token lives in staging Firestore and is shared by both apps anyway, since they use the same backend and user).
- **B. Per-identity scheme** (e.g. `blackhorsecyclingapp-dev`). Needs `REDIRECT_URI` built from the scheme, and David adding `blackhorsecyclingapp-dev://oauth/intervals` to the staging Intervals.icu app. That's a manual request with an unknown turnaround.

Because both apps share the staging backend and user, the Intervals.icu connection made from either app serves both. So option A costs little: if the chooser appears, pick either app. **Recommendation: A**, and revisit if it bites.

## One-time owner steps (all free)

1. Firebase console (or CLI), project `bh-cycling-staging`: add iOS app `com.wojtas.blackhorsecyclingapp.dev` and Android app `com.wojtas.blackhorsecyclingapp.dev`.
2. Run the first `eas build --profile dev` interactively on each platform. It creates the Apple App ID, the ad hoc profile and the Android keystore.
3. `eas credentials` → copy the Android SHA-1 → add it to the Firebase Dev Android app.
4. Download the Dev `GoogleService-Info.plist` and the refreshed `google-services.json`. Upload them as Sensitive EAS file variables in the `development` environment.
5. `eas device:create` for each phone, then rebuild (or `eas build:resign`) so the profile includes the phones.
6. For CI to pick up newly added devices: an App Store Connect API key as GitHub secrets, plus `--refresh-ad-hoc-provisioning-profile` on Dev iOS builds. Optional if the device list rarely changes.
