# Research: a Toast that renders above everything (iOS + Android)

Follow-up to `docs/research/toast-mechanisms.md` (branch `research/toast-mechanisms`).
Date: 2026-10-11. Facts only. No final choice is made here.

New hard requirement: the global Toast must be visible **above everything** on iOS and Android. That includes native modal and formSheet screens, RN `<Modal>`, and the `@expo/ui` `BottomSheet` (a SwiftUI `.sheet` on iOS and a Compose `ModalBottomSheet` Dialog on Android). The earlier requirements still apply: non-interactive, success/warning/error variants with a themed icon and colour, a single message, persists across navigation, and an imperative module-level API.

Stack: `react-native 0.86.3` (New Architecture), `expo ~57`, `expo-modules-core 57.0.20`, `react-native-screens 4.26.2`, `react-native-reanimated 4.5.1`.

How sources were read: package tarballs from `npm pack` (latest versions on 2026-10-11), GitHub repos and issues through `gh`, AOSP sources from `android.googlesource.com` (`main`), Apple docs JSON from `developer.apple.com/tutorials/data/documentation/...`, and RN, `@expo/ui` and `expo-modules-core` sources in this repo's `node_modules`.

## TL;DR

- **iOS rule: the view that was added to the window last is on top.**
  - Every native presentation (RNS modal/formSheet, SwiftUI `.sheet`, RN `<Modal>`) lives in a `UITransitionView` that is added to the **same** `UIWindow` _after_ existing subviews.
  - So anything added to the window _after_ the sheet is presented is above it. That covers SPIndicator/Burnt, and a `FullWindowOverlay` that is **mounted at show time** rather than kept mounted.
  - A **separate `UIWindow` with a higher `windowLevel`** is above _everything_ in the main window, whatever the order (react-native-simple-toast does this at `UIWindowLevelAlert + 1`).
- **Android rule: the window that was added last is on top.**
  - AOSP `ActivityRecord.isFirstChildWindowGreaterThanSecond` says: "Otherwise the new window is greater than the existing window".
  - A Compose `ModalBottomSheet` and an RN `<Modal>` are `ComponentDialog`s, which are `TYPE_APPLICATION` windows on the Activity token.
  - So a `TYPE_APPLICATION` window added _after_ the sheet, through the Activity's `WindowManager`, is drawn above it. This needs no `SYSTEM_ALERT_WINDOW` permission, and with `FLAG_NOT_TOUCHABLE | FLAG_NOT_FOCUSABLE` it does not take touches or focus.
  - react-native-z-view uses exactly this, and hosts React-rendered children in that window.
- **toastify-react-native** gets "above modals" by rendering inside RN `<Modal transparent>` by default (`useModal: true`). The cost:
  - It **blocks all touches** for the whole time the toast is visible (confirmed by the maintainer in issues #58, #71 and #81).
  - On Android, the Modal takes window focus.
  - On iOS, a root-mounted Modal cannot present while another view controller is already being presented from the same presenter. UIKit logs "Attempt to present … which is already presenting …" (RN issue #3445).
- **No maintained library found does all of this:** custom-styled toasts, above all native sheets, without blocking touches, on both platforms.
  - react-native-z-view comes closest by mechanism. It is unmaintained (last push 2023-10) and uses a legacy ViewManager on Android.
  - A small custom Expo module is feasible. Both platforms have direct precedents: simple-toast's UIWindow, z-view's and RN Modal's separate Android windows, and `@expo/ui` `RNHostView`, which hosts RN children in other view controllers and Dialog windows.

## 1. `toastify-react-native`

Source: tarball `toastify-react-native@7.2.3` (`components/ToastManager.tsx`, `index.ts`, `utils/interfaces.ts`, `components/BaseToast.tsx`, `README.md`) and [GitHub issues](https://github.com/zahidalidev/toastify-react-native/issues).

- **Version and maintenance:**
  - `7.2.3` is the latest. It was published, and the repo last pushed, on 2025-07-20, so there have been no commits for about 15 months.
  - The repo has 242 stars and 22 open issues. Issues filed since then have no maintainer replies, for example #83 (2026-05), #82 (2026-01) and #81 (2025-12).
- **Rendering:**
  - `ToastManager.render()` wraps the toast in RN `<Modal visible transparent animationType>` when `useModal` is true, which is the default ("Default to true for backward compatibility").
  - With `useModal: false` it renders an absolutely positioned `TouchableOpacity` in place, at the ToastManager's position in the tree.
  - It does not use `FullWindowOverlay`, and it has no native code. Animation uses the RN `Animated` API (progress bar) and the Modal's `animationType` ('fade' | 'slide' | 'none').
- **Above native modals and sheets:**
  - The README "Modal Behavior" section says: "With Modal (`useModal: true`): The toast appears with a modal overlay, making the background screen non-interactive. This ensures the toast is always visible, even over other modals, but prevents users from interacting with content behind it." It also says: "Without Modal … the toast might not appear over other modal components."
  - The maintainer, in issue #58, wrote: "In React Native, **only a `Modal` can appear above another `Modal`**".
  - Issue #71 (Expo Router root layout): "While the toast is being displayed I cannot touch the rest of the UI". Maintainer: "because the `ToastManager` uses a `Modal` by default, which blocks background interaction."
  - Issue #81: "can't scroll the page when the toast appears". Suggested fix: `useModal: false`.
  - **Android mechanics** (RN 0.86 `ReactModalHostView.kt`):
    - Each RN Modal is a new `ComponentDialog` with a full-screen theme (`Theme_FullScreenDialog*`). `FLAG_NOT_FOCUSABLE` is cleared after `show()`.
    - It never sets `FLAG_NOT_TOUCH_MODAL`, so by the AOSP doc it "will consume all pointer events itself".
    - Because it is the newest app window, it sits above an already-open Compose sheet Dialog (section 4b). The cost is that it blocks touches and takes focus. Back/Escape go to the toast Modal's `onRequestClose`, which toastify wires to `hide`.
  - **iOS mechanics** (RN 0.86 `RCTModalHostViewComponentView.mm`):
    - `transparent` maps to `UIModalPresentationOverFullScreen`.
    - It presents with `[[self reactViewController] presentViewController:…]`. `reactViewController` walks the responder chain to the _nearest_ view controller (`UIView+React.m`).
    - For a ToastManager mounted in the root layout, that is a root-level view controller. If that controller is already presenting something (an RNS modal or formSheet, a SwiftUI sheet, another RN Modal), UIKit refuses with "Warning: Attempt to present <RCTModalHostViewController> on <UIViewController> which is already presenting …". See [RN #3445 "Multiple Modal components"](https://github.com/facebook/react-native/issues/3445).
    - The RN fix PR ([#31498](https://github.com/facebook/react-native/pull/31498), "mount each modal into a new UIWindow") was **closed unmerged**.
    - [RNS #525](https://github.com/software-mansion/react-native-screens/issues/525) has a user report that a root RN Modal over a native-stack modal is "just invisible and dismisses almost right after mounted". In the same thread, an RN Modal rendered _inside_ the modal screen works.
    - Taken together, the README claim "always visible, even over other modals" depends on where `<ToastManager>` is mounted on iOS. This was not checked on a device here.
- **Variants:**
  - `ToastType = 'success' | 'error' | 'info' | 'warn' | 'default'`.
  - The calls are `Toast.success(text, position?, icon?, iconFamily?, useModal?)`, `Toast.error`, `Toast.info`, `Toast.warn` and `Toast.show({ type, text1, text2, ... })`.
- **Theming and custom render:**
  - `theme: 'light'|'dark'`, plus per-call `backgroundColor`, `textColor`, `iconColor`, `iconSize`, `icon` (string or ReactNode), `progressBarColor`, `style`, and `icons` per type.
  - `config` maps a type to `(params) => ReactNode` for fully custom components, so a Restyle-themed component is possible.
  - The default colours are hard-coded in `config/theme.ts`. The built-in look includes a close icon and a progress bar, which can be turned off with `showCloseIcon` / `showProgressBar`.
  - Even with a custom `config` render, the Modal wrapper wraps the content in a `TouchableOpacity` that pauses on press-in.
- **Imperative API outside React:**
  - `index.ts` creates a module-level `createRef` and exports `Toast.{show,hide,success,error,info,warn}`. These can be called anywhere once `<ToastManager />` is mounted.
  - Calls before mount are silently dropped (`toastRef.current?.show`).
- **Queue and stack:** none. `show()` calls `this.hide()` first and replaces the current toast, so only one is visible. Issue #62 ("How to show multiple toasts at the same time?") is open.
- **New Architecture:** pure JS (RN `Modal`, `Animated`, `TouchableOpacity`), with no native module, so it runs on Fabric through the standard components. It has no explicit New Architecture statement.
- **Dependencies and rebuild:**
  - `dependencies: { "react-native-vector-icons": "*" }`. `BaseToast` `require`s `react-native-vector-icons/<Family>`.
  - `react-native-vector-icons@10.3.0` is **deprecated** on npm ("moved to a new model of per-icon-family packages").
  - Vector-icon fonts need native font linking. In Expo, fonts must be loaded or embedded, and a config change or rebuild may be needed. Issue #80: "The icons are not loading (looks like chinese characters)". Issue #47: "Make the icon dependency optional" (open).
  - It ships TS source (`main: index.ts`). Typing issues are open: #70 and #72 "useModal is missing from ToastManager's type".

### 2b. Patterns that work above everything (from the sources above)

- **iOS, separate `UIWindow`** (simple-toast): a `UIWindow` subclass created with `initWithWindowScene:`, using the foreground-active `UIWindowScene` and falling back to `initWithFrame:keyWindow.bounds`. It sets `windowLevel = UIWindowLevelAlert + 1` and `hidden = NO`. `hitTest:` returns `nil` when the hit view is the window itself, so touches outside the toast fall through to the app window.
- **iOS, late `addSubview` to the key window** (SPIndicator/Burnt): above anything presented _before_ the toast. A sheet presented _during_ the toast covers it.
- **Android, a newer app window on the Activity token** (z-view, and RN Modal itself): `WindowManager.addView` with `TYPE_APPLICATION` from an Activity context. It is above Dialogs added earlier, without any permission.
- **Android system toast** (`ToastAndroid`, used by Burnt and simple-toast): above app windows, but without custom styling (see the prior doc).

## 3. `FullWindowOverlay` (react-native-screens 4.26.2) and the transparent RN `<Modal>` host

### 3a. Does FWO create a separate `UIWindow`? **No.**

Source: `ios/RNSFullWindowOverlay.mm` (tarball 4.26.2):

- `maybeShow` takes `[self window]` (falling back to `RCTKeyWindow()`), then `if (![[window subviews] containsObject:_container]) [window addSubview:_container];`. The container is an `RNSFullWindowOverlayContainer : UIView` added as a **subview of the app's existing window**, with no new `UIWindow` and no `windowLevel`.
- `maybeShow` is called from `didMoveToWindow`, and from `didMoveToSuperview` as a fallback. `didMoveToSuperview` with `superview == nil` calls `[_container removeFromSuperview]`, and so does `prepareForRecycle`.
- The container's `pointInside` returns YES only over subviews that are user-interaction-enabled, so touches pass through elsewhere. It attaches its own `RCTSurfaceTouchHandler`.
- The JS side (`src/components/FullWindowOverlay.tsx`) returns a plain `<View>` and logs `'Using FullWindowOverlay is only valid on iOS devices.'` on Android.

### 3b. Can FWO end up above later-presented view controllers?

- Native presentations are added to the same window in a `UITransitionView` at a higher index. [RNS PR #3553](https://github.com/software-mansion/react-native-screens/pull/3553): "Separate `UITransitionView` is created and attached at higher index under `UIWindow` presenting `fullScreenModal` contents".
- **A FWO that is always mounted** was added before the sheet, so the sheet's transition view is above it. This matches the sonner-native docs quoted in the prior research.
- **A FWO mounted at the moment the toast shows** runs `[window addSubview:_container]` _after_ the sheet's transition view, so it is above it:
  - [RNS #3521](https://github.com/software-mansion/react-native-screens/issues/3521) repro: root-level `{isVisible && <FullWindowOverlay>…}` toggled from inside a modal screen. The reporter: "No problem with `presentation: 'modal'`". `fullScreenModal` was broken in 4.19 and fixed by PR #3553, which added the `didMoveToSuperview` + `RCTKeyWindow()` fallback that is present in 4.26.2.
  - Edge cases: a sheet presented _while_ the toast is visible goes above it. Re-showing a toast with a FWO that is still mounted does not re-add it (`containsObject` check), so the host would have to unmount between toasts, or be keyed per toast. Multi-window iPad can pick the wrong window (RNS #3372, which PR #3553 says "might" come back in corner cases).
  - This was not verified here with the `@expo/ui` SwiftUI `BottomSheet`. `@expo/ui`'s own `RNHostView.swift` comment says the sheet "presents its content in its own view controller". By the UIKit model above, that means the same window and a later transition view, but this is not proven.
- FWO cannot be placed above a presentation that happens _after_ it is attached, because it has no window level. Only a separate `UIWindow` with a higher `windowLevel` is independent of order. Apple `UIWindow.windowLevel`: "All windows assigned to the same window level appear in front of (or behind) all windows assigned to a different window level. The ordering of windows within a given window level is not guaranteed."

### 3c. Transparent RN `<Modal>` as the toast host

- **Touch pass-through: no** on either platform.
  - iOS: it is a presented `UIModalPresentationOverFullScreen` view controller whose root view covers the screen.
  - Android: a full-screen `ComponentDialog` without `FLAG_NOT_TOUCH_MODAL`, which by the AOSP doc means it "will consume all pointer events itself, regardless of whether they are inside of the window". It is also focusable after `show()`.
  - [react-native-z-view README](https://github.com/intergalacticspacehighway/react-native-z-view): "[RN Modal] blocks the touch of behind views … so it is not a great solution for custom Toast". toastify issues #58, #71 and #81 show the same behaviour in practice.
- **Presentation stacking:**
  - iOS presents from the nearest view controller of the Modal's host view. A root-mounted Modal cannot present while that controller is already presenting (RN #3445). It works only when the Modal is mounted inside the topmost presented content.
  - Android stacks naturally: the newest Dialog window is on top.
- **Side effects:** the presentation and dismissal animations and focus changes are those of a modal, not a toast. On Android, back presses are routed to the toast Modal while it is visible.

## 4. Custom Expo module (Swift + Kotlin): feasibility

### 4a. iOS: dedicated `UIWindow`

- Create `UIWindow(windowScene:)` from the active scene. Apple: "Creates a window and associates it with the specified scene object". The scene can come from `keyWindow?.windowScene`. `expo-modules-core` 57 has `SceneGeometry.keyWindow(for:)` and `appContext.utilities.currentViewController()`.
- Set `windowLevel` above `.normal`. Simple-toast uses `UIWindowLevelAlert + 1`, which also puts it above `UIAlertController`-style windows at alert level. Set `isHidden = false` and do not call `makeKeyAndVisible`, so the window does not become key and the app window keeps keyboard focus. Simple-toast only calls `setHidden:NO`.
- Pass-through: either set `isUserInteractionEnabled = false` on the window or toast view (the toast is non-interactive), or override `hitTest` to return `nil` for the window itself (simple-toast). Apple `hitTest(_:with:)`: "This method ignores view objects that are hidden, that have disabled user interactions, or that have an alpha level less than 0.01."
- Result: above every presentation in the main window (RNS modal/formSheet, SwiftUI sheet, RN Modal), whatever the order, because the window level is higher (`windowLevel` doc, section 3b).
- Precedents: react-native-simple-toast (about 300 lines of Obj-C including the scalessec/Toast pod), and the RN PR #31498 approach, unmerged, of putting each modal in a new `UIWindow`.

### 4b. Android: above a Compose `ModalBottomSheet` Dialog without `SYSTEM_ALERT_WINDOW`

AOSP facts (`core/java/android/view/WindowManager.java`, `core/java/android/view/Window.java`, `services/.../wm/WindowToken.java`, `services/.../wm/ActivityRecord.java`, branch `main`):

- `TYPE_APPLICATION`: "a normal application window. The `token` must be an Activity token". `LayoutParams()` defaults `type = TYPE_APPLICATION`, and `Dialog` uses that default. `Window.adjustLayoutParamsForSubWindow` fills `wp.token = mAppToken` for application-type windows.
- The Compose sheet is `ModalBottomSheetDialogWrapper : ComponentDialog(ContextThemeWrapper(composeView.context, …))` ([androidx `ModalBottomSheet.android.kt`](https://github.com/androidx/androidx/blob/androidx-main/compose/material3/material3/src/androidMain/kotlin/androidx/compose/material3/ModalBottomSheet.android.kt)). That makes it an application window on the Activity token. `@expo/ui` `ModalBottomSheetView.kt` uses Compose `ModalBottomSheet` and reads the `DialogWindowProvider` window.
- Z-order within the Activity token: `ActivityRecord.isFirstChildWindowGreaterThanSecond` puts base application windows below others and starting windows above, then: "Otherwise the new window is greater than the existing window." (`WindowToken` base: "New window is considered greater if it has a higher or equal base layer.") **So a `TYPE_APPLICATION` window added after the sheet is above it, and a Dialog shown after the toast is above the toast.**
- Sub-window types: `FIRST_SUB_WINDOW` windows "must be set to the window they are attached to … kept next to their attached window in Z-order". `TYPE_APPLICATION_PANEL`: "appear on top of their attached window". `TYPE_APPLICATION_SUB_PANEL`: "on top their attached window and any `TYPE_APPLICATION_PANEL` panels". `TYPE_APPLICATION_ATTACHED_DIALOG`: "like `TYPE_APPLICATION_PANEL`, but layout … as that of a top-level window". A sub-panel attached to the Activity decor is next to the _Activity_ window, not above a separate Dialog window. To be above the sheet it would have to attach to the sheet's own window token, which means finding the topmost window. `PopupWindow` defaults to `TYPE_APPLICATION_PANEL` with the anchor view's token. This is an inference from these docs and was not tested.
- `TYPE_APPLICATION_OVERLAY` "Requires `SYSTEM_ALERT_WINDOW` permission". It is not needed for the approach above.
- Flags for a non-interactive toast:
  - `FLAG_NOT_TOUCHABLE`: "this window can never receive touch events". Since Android 12, touches that pass through are delivered if the window has the same UID, which it does here.
  - `FLAG_NOT_FOCUSABLE`: "won't ever get key input focus … will also enable `FLAG_NOT_TOUCH_MODAL` … gets Z-ordered on top of the input method".
  - Use `PixelFormat.TRANSLUCENT`.
- Precedents: react-native-z-view `ZView.java`, and RN's own Modal, which hosts React content in a separate `ComponentDialog` window with a `DialogRootViewGroup`.
- Android limits (inferred): the toast window belongs to the current Activity. It must be removed on Activity destroy or configuration change (`WindowLeaked` otherwise), and a Dialog opened while the toast is visible goes above it.

### 4c. Native-drawn versus React-rendered content

- **Native-drawn** (Swift `UIView`/SwiftUI and Kotlin `View`/Compose): the module receives `{ variant, message }` and the theme colours and icon names as plain values. There is no layout or touch plumbing. Theming comes from JS-passed tokens (hex colours, SF Symbol / Material icon names or image assets).
- **React-rendered** (an Expo native view whose children are moved into the toast window), with precedents:
  - iOS RNS FWO moves its Fabric children into a container added to the window and attaches `RCTSurfaceTouchHandler`.
  - Android z-view and RN Modal move children into a root view in another window and use `JSTouchDispatcher`.
  - `@expo/ui` `RNHostView` (Swift and Kotlin, `expo-modules-core` 57) hosts RN children inside SwiftUI sheets, popovers and Compose dialogs. Its comments describe the touch and `measure()` coordinate handling needed when "Presented in its own view controller".
  - A non-interactive toast needs no touch dispatch at all (`FLAG_NOT_TOUCHABLE` / `userInteractionEnabled = false`), which removes the hardest part.
  - Remaining concern: Fabric still owns these views (recycling, layout from Yoga in surface coordinates). RNS handles this with `prepareForRecycle` / `didMoveToSuperview`. Not prototyped here.
- **Mixed, no native code:** iOS mount-at-show FWO (section 3b) plus Android z-view-style window. This still needs native code for the Android part.
