## TL;DR

- `GET /api/v1/activity/{id}` returns the **full `Activity`** (184 properties in the spec). It has **no `fields` projection**. Its only query parameter is `intervals` (boolean). `?intervals=true` returns `ActivityWithIntervals`, which is the same object plus `icu_intervals` and `icu_groups`. One request gives the metrics, the description and the recorded intervals. [SPEC]
- An Activity has **no `workout_doc`**. In the spec, `workout_doc` exists only on `Event`, `EventEx`, `Workout` and `WorkoutEx`. An unplanned Activity has **no planned structure and no targets**. [SPEC]
- What it does have is **recorded intervals**. Each one has `start_time`/`end_time` (seconds from the start), `moving_time`/`elapsed_time`, `average_watts`, `weighted_average_watts`, `intensity` (most likely %FTP), `zone` with `zone_min_watts`/`zone_max_watts`, `type` (`WORK` | `RECOVERY`), `label`, HR, cadence and speed. Intervals do not overlap ([DM]). This is enough to draw a time-ordered **recorded** profile (bars at the measured %FTP) and a "Kroki"-like list of measured segments. It is not a plan.
- `description` is a plain field on the Activity. Comments are a separate thing (`icu_chat_id` → `GET /activity/{id}/messages`).
- **Strava stubs:** both the list and the single endpoint return a `Hidden` stub `{id, icu_athlete_id, start_date_local, source:"STRAVA", _note:"STRAVA activities are not available via the API"}`. The stub has no `type`, `name`, metrics or intervals. _Inferred:_ the status is 200, not 404.
- **Missing or deleted id:** _inferred_ `404`. The app's `request()` already turns that into `IntervalsApiError(404)`, and `isNotFoundError` detects it. Error bodies are JSON like `{"status":401,"error":"Unauthorized"}` [HDR].
- **Scope:** `ACTIVITY:READ`, which the app already requests, should be enough ([D-80090] for the list endpoint; _inferred_ for the single endpoint and `/intervals`).

## 1. Endpoints

**No fields projection on the single endpoint (confirmed).** The full object comes back every time. Some of its parts are large: `skyline_chart_bytes`, zone arrays, `icu_achievements` and the weather fields. _Inferred size:_ a few KB to tens of KB. Size alone doesn't justify a workaround. If it ever did, the list endpoint with `oldest=newest=<the day>` and `fields=` could stand in for the metrics, but it can't return intervals.

## 2. Summary fields behind the existing metric set

All 14 `ACTIVITY_METRIC_FIELDS` entries in `lib/workoutDetails.ts`, plus `icu_joules` and `compliance` from `WORKOUT_DETAILS_ACTIVITY_FIELDS`, are top-level properties of `Activity` in [SPEC]:

| Metric key         | Field                    | Spec type | Notes                                                                                                                                          |
| ------------------ | ------------------------ | --------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `movingTime`       | `moving_time`            | integer s |                                                                                                                                                |
| `distance`         | `distance`               | number m  | [DM] says "Use this one for distance" about `icu_distance`. Both exist. The app uses `distance`.                                               |
| `load`             | `icu_training_load`      | integer   | `power_load` / `hr_load` / `pace_load` hold the per-source split.                                                                              |
| `intensity`        | `icu_intensity`          | number %  | [DM]: legacy `intensity` → "Use icu_intensity instead".                                                                                        |
| `averagePower`     | `icu_average_watts`      | integer W |                                                                                                                                                |
| `normalizedPower`  | `icu_weighted_avg_watts` | integer W | [DM]: "Normalized watts".                                                                                                                      |
| `averageHeartRate` | `average_heartrate`      | integer   |                                                                                                                                                |
| `maxHeartRate`     | `max_heartrate`          | integer   |                                                                                                                                                |
| `cadence`          | `average_cadence`        | number    | rpm for rides. _Inferred:_ for runs this is steps per minute (or strides per minute, depending on the device). It's the same field either way. |
| `elevationGain`    | `total_elevation_gain`   | number m  |                                                                                                                                                |
| `calories`         | `calories`               | integer   |                                                                                                                                                |
| `averageSpeed`     | `average_speed`          | number    | [DM]: "In m/s. Uses moving time if available otherwise elapsed time."                                                                          |
| `elapsedTime`      | `elapsed_time`           | integer s |                                                                                                                                                |
| `variabilityIndex` | `icu_variability_index`  | number    |                                                                                                                                                |

**By sport (Run, WeightTraining, VirtualRide).** There is **one `Activity` schema for every sport** [SPEC]. Sport doesn't change the shape. It only changes which fields have values (_inferred_):

- **VirtualRide / Ride with power:** everything above is filled, plus `icu_ftp`, `icu_power_zones` and `icu_zone_times`. `trainer` is true for a VirtualRide (#132).
- **Run:** power fields are null unless there's a running power meter. Run-only fields appear: `pace`, `gap`, `threshold_pace`, `pace_zone_times`, `gap_zone_times`, `average_stride`, `average_stance_time` and the other running-dynamics fields. `pace_load` may be the load source.
- **WeightTraining:** usually no power, distance or speed. Often only `moving_time`/`elapsed_time`, HR (if a strap was worn), `calories` and `icu_training_load` (from HR). It has its own field, `kg_lifted`. Manual entries (`source: "MANUAL"`) may carry only duration and load.
- The existing `activityMetrics()` already skips any non-finite value, so a missing metric stays missing for every sport. It isn't shown as zero.

Other fields that could help an Activity Details screen: `name`, `description`, `type`, `sub_type` (`NONE|COMMUTE|WARMUP|COOLDOWN|RACE`), `trainer`, `race`, `commute`, `device_name`, `source`, `icu_ftp` (the FTP in force for this Activity), `icu_power_zones` (zone tops as %FTP, [DM]), `icu_zone_times` (`{id, secs}[]`, seconds in each power zone), `icu_hr_zone_times`, `interval_summary` (`string[]`, presumably short labels such as "3x 5m 300w", _inferred format_), `icu_lap_count`, `perceived_exertion` / `icu_rpe`, `feel`, `stream_types`, `max_speed`, `max_watts`-like peaks (`p_max`), `decoupling`, `icu_efficiency_factor`, `tags`, `icu_chat_id`.

## 3. Structure: what could feed a Workout Profile or Kroki

### 3a. No `workout_doc` on an Activity (confirmed)

Neither `Activity` nor `ActivityWithIntervals` defines `workout_doc`. Its only owners in [SPEC] are `Event`, `EventEx`, `Workout` and `WorkoutEx`. Nothing in the spec suggests a Zwift or structured ride's Activity carries its plan. The plan lives on the calendar event, and the Activity points to it through `paired_event_id`. An unplanned Activity has no event by definition, so **there is no planned structure and no targets (no %FTP targets, no ramps)**. The only planned-workout trace on an Activity is `workout_shift_secs` ([DM]: "How much to adjust the start of the workout relative to the activity"), which only matters when the Activity is paired.

_Inferred, not checked:_ a Zwift or Garmin structured-workout FIT file carries the workout's step boundaries as **laps**. intervals.icu can build its intervals from laps (see 3c). This shapes the recorded intervals, but it doesn't add any targets.

### 3b. Recorded intervals (`icu_intervals`)

Recorded intervals come from `?intervals=true` or `GET /activity/{id}/intervals`. [DM] describes them as "Stats for a portion of an activity. **Intervals do not overlap.**" Fields worth using ([SPEC] `Interval`, 84 properties; example values from David's sample in [D-609] #14):

| Field                                                                                                                                                                                                | Meaning                                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`                                                                                                                                                                                                 | integer                                                                                                                                                                                                                                                                                                                                                |
| `type`                                                                                                                                                                                               | `WORK` \| `RECOVERY` (spec enum). [DM]: "Intervals can be work or recovery. How this is assigned depends on the algorithm."                                                                                                                                                                                                                            |
| `label`                                                                                                                                                                                              | string, optional (a user's name for the interval)                                                                                                                                                                                                                                                                                                      |
| `start_time`, `end_time`                                                                                                                                                                             | seconds from the start of the activity. [DM]: don't use these to index streams, use `start_index`/`end_index` for that. **Good for time-ordering and widths.**                                                                                                                                                                                         |
| `start_index`, `end_index`                                                                                                                                                                           | stream indexes (end exclusive)                                                                                                                                                                                                                                                                                                                         |
| `moving_time`, `elapsed_time`                                                                                                                                                                        | s                                                                                                                                                                                                                                                                                                                                                      |
| `distance`                                                                                                                                                                                           | m                                                                                                                                                                                                                                                                                                                                                      |
| `average_watts`, `weighted_average_watts`, `min_watts`, `max_watts`, `average_watts_kg`, `max_watts_kg`                                                                                              | W                                                                                                                                                                                                                                                                                                                                                      |
| `intensity`                                                                                                                                                                                          | integer, e.g. `112`. **_Inferred_ to be %FTP.** David's sample has `average_watts` 327 = `weighted_average_watts` 327, `intensity` 112, `zone` 5 with `zone_min_watts` 305 and `zone_max_watts` 348. That fits FTP ≈ 292 W (327/292 = 112 %) and a Z5 of 105–120 % (306–350 W). The sample can't tell whether it's average or weighted power over FTP. |
| `zone`, `zone_min_watts`, `zone_max_watts`                                                                                                                                                           | the power zone that holds the interval's power, with its watt bounds                                                                                                                                                                                                                                                                                   |
| `training_load`, `joules`, `joules_above_ftp`, `decoupling`, `w5s_variability`, `wbal_start`, `wbal_end`                                                                                             |                                                                                                                                                                                                                                                                                                                                                        |
| `average_heartrate`, `min_heartrate`, `max_heartrate`, `average_cadence`, `min_cadence`, `max_cadence`, `average_speed`, `min_speed`, `max_speed`, `gap`, `average_gradient`, `total_elevation_gain` |                                                                                                                                                                                                                                                                                                                                                        |
| `group_id`                                                                                                                                                                                           | links to an `icu_groups` entry, e.g. `"719s@327w72rpm"`                                                                                                                                                                                                                                                                                                |

`icu_groups` (`IntervalGroup`) are averaged stats for groups of similar intervals, with `id` (string) and `count`. They could feed a compact "5 × 4 min @ 310 W" line.

**Coverage (inferred).** Do intervals span the whole ride, or only the efforts? `type: RECOVERY` exists, and [DM] says intervals don't overlap. On intervals.icu's own activity page, the detected intervals usually alternate WORK and RECOVERY across the ride, but a gap-free timeline is **not guaranteed**. A builder should sort by `start_time` and fill any gap as an "unclassified" segment (or leave it blank) instead of assuming the intervals tile the ride. A steady endurance ride may have **one or zero** intervals. A Run's intervals carry pace and speed fields, and power only with a running power meter. A WeightTraining or manual Activity most likely has **no intervals at all**, since there are no streams to analyse.

### 3c. Laps

[DM] has `Activity.laps?: ActivityLap[]` (`start_index`, `end_index`, `name`, `intensity: ACTIVE|REST|WARMUP|COOLDOWN|RECOVERY|INTERVAL|OTHER`) and says: "Lap information from the original file. When an activity is analyzed with use laps set then the start and end of each interval is taken from the laps." **The current [SPEC] `Activity` has no `laps` property**, only `icu_lap_count`. _Inferred:_ laps aren't returned by the API today. Use `icu_intervals`, which already follow the laps when the athlete chose "use laps".

### 3d. What this means for each section

- **Profile.** No planned profile. A **recorded** profile can be built from `icu_intervals`: x = `start_time`..`end_time`, height = `intensity` (%FTP, _inferred_) or `average_watts / activity.icu_ftp × 100`, colour = `zone` or the existing zone bands from `icu_power_zones`. It goes through a new adapter, not `buildWorkoutProfile`, which expects `WorkoutStep` with `power` targets. The adapter must handle gaps and the no-interval or no-power cases (Run without power, WeightTraining). In those cases the section is hidden. Showing a power-zone strip from `icu_zone_times` instead would be a product decision. Drawing a true power trace would need the `watts` stream (see #132), which is a heavier request.
- **Kroki.** No planned steps. A "recorded intervals" list (type, duration, avg W / %FTP, avg HR) is possible from `icu_intervals`, with `icu_groups` as an optional summary. This isn't the same thing as Kroki, so the section probably needs a different name.
- **Metrics.** The 14 existing metric keys all map 1:1, so `activityMetrics()` can be reused as it is. There is no Plan vs wykonanie (no event) and no `compliance`.
- **Opis.** `activity.description` (string) is the Activity's own text. It is set on upload (`description` parameter, [D-80090]) or edited on intervals.icu. For Strava-sourced data it is never available. _Inferred:_ it is often empty for device uploads. Comments are separate (`icu_chat_id` + `/messages`). Note that [PRIOR] `workout-details-fields.md` §2 said "Post-ride notes and comments are not a field". That is true for comments, but `description` **is** a field.

## 4. Strava-synced stubs

- [SPEC] says "An empty stub object is returned for Strava activities" on both `listActivities` and `getActivity`. The single endpoint's `oneOf` includes `Hidden` = `{ id, icu_athlete_id, start_date_local, source, _note }`.
- Observed stub: `"source": "STRAVA"`, `"_note": "STRAVA activities are not available via the API"` ([D-609] #498, 2024-12-14). David's reason: "I have to be very careful here or Intervals.icu will lose access to the Strava API" (#504). Activity webhooks are not delivered for Strava activities either ([D-80090]).
- **Fields present:** only the five above. The stub has **no `type`, `name`, `moving_time`, `distance`, `paired_event_id`, `description` or intervals**. With `fields=` on the list endpoint, only the requested fields that the stub has come back, because nulls are dropped. _Inferred._
- **Status:** _inferred_ **200** with the stub body, since the spec says a stub "is returned", not an error. It's not a 404. _Unverified:_ whether `/activity/{id}/intervals` for a Strava activity returns an empty `IntervalsDTO`, a stub or a 4xx.
- **Detection:** `source === 'STRAVA'` together with no `type` (or `_note` present). The app's `IntervalsActivity` type marks `name`, `type`, `moving_time` and `distance` as required, which isn't true for stubs. Activity Details should show a degraded "available on Strava only" state. The Calendar's `joinCalendarItems` already turns every unpaired Activity into an Unplanned Activity, so a stub shows up there with no name or type. That's worth checking in the Calendar too (outside #158's scope).

## 5. Errors and scope

- **Error body shape (observed for 401):** `content-type: application/json`, body `{"status":401,"error":"Unauthorized"}` [HDR]. _Inferred:_ other errors use the same Spring-style `{status, error, ...}` body. The app ignores the body and only reads the status, so this doesn't matter.
- **Missing or deleted id:** _inferred_ **404**. This matches the documented behaviour of the calendar-event endpoint the app already relies on (`getCalendarEvent`: "A deleted or unknown event surfaces as an `IntervalsApiError` with status 404") and the #132 finding that 404 means "activity id unknown". The spec has a `DELETE /activity/{id}/tombstone` endpoint, so deleted activities leave a tombstone. _Unverified:_ whether a tombstoned id returns 404 or something else (410, 403, or a stub). An id belonging to another athlete most likely returns 403 or 404. Activity Details should handle any 4xx other than 401 as "this Activity is gone" and use `isNotFoundError` for the explicit 404 case.
- **Scope:** [D-80090]: "Call the list activities endpoint (ACTIVITY:READ scope is required)". The spec has no per-endpoint scopes. Scopes cover whole data areas, so `GET /activity/{id}`, `/intervals` and `/messages` should all fall under `ACTIVITY:READ` (_inferred_, as in #132). The app already requests `ACTIVITY:READ,CALENDAR:READ` (`hooks/useIntervalsAuth.ts`), so **no reconnect** is needed.

## 6. Suggested app shape (non-binding)

- Add `getActivity(token, activityId, { intervals: true })` plus `intervalsActivityPath(id)` = `/activity/${id}`. The path has no athlete id, so the request doesn't need one.
- Widen `IntervalsActivity`, or add an `IntervalsActivityDetail` type, with `description?`, `icu_ftp?`, `icu_power_zones?`, `icu_intervals?: IntervalsActivityInterval[]`, `source?` and `_note?`. Make `name` and `type` optional (or narrow the type by detecting stubs first).
- Pure builders for the recorded profile and the interval list, unit-tested against fixture JSON (business logic only, per CODING_STANDARDS.md).
